# Operations runbook

Running MagnetAI in production: deploying, monitoring, backing up, and responding
when something breaks.

---

## Processes

Three backend processes, each scaled independently:

| Process | Command | Scaling |
|---|---|---|
| API | `uvicorn app.main:app --proxy-headers --forwarded-allow-ips '*'` | Horizontal; stateless |
| Worker | `celery -A app.platform.celery_app worker --concurrency=2` | Horizontal; add for build throughput |
| Beat | `celery -A app.platform.celery_app beat` | **Exactly one** |

`--proxy-headers` is required behind a load balancer: without it every request
appears to come from the balancer, and per-IP rate limiting collapses into one
shared bucket.

Beat is the scheduler. Running two would double-schedule the heal sweep — the
cluster-wide lock prevents actual duplicate work, but it is still misconfiguration.

Workers recycle after 50 tasks (`worker_max_tasks_per_child`) so a leak in an AI or
Node SDK cannot grow unbounded.

---

## Deploying

Order matters. Migrations first, then workers, then the API.

```bash
# 1. Back up (see Backups) — always, before any migration.

# 2. Apply migrations from a one-off container/task, not from a serving process.
alembic upgrade head

# 3. Roll workers and beat, then the API.
```

Why this order: the API is the only process users touch, so it should be last to
change and first to be rolled back. Migrations must be additive within a release
(add columns before code reads them, drop them a release later) so an API rollback
never faces a schema it cannot handle.

### Pre-deploy checklist

- [ ] `MAGAI_ENVIRONMENT=production`
- [ ] `MAGAI_SECRET_KEY` set to a random 32+ character value (32+ enforced at boot)
- [ ] `MAGAI_CORS_ALLOW_ORIGINS` lists exact production origins, no `*`
- [ ] `MAGAI_TRUSTED_HOSTS` lists real domains
- [ ] `MAGAI_LOG_FORMAT=json`
- [ ] `MAGAI_ALLOW_PRIVATE_TARGET_URLS=false`
- [ ] `MAGAI_GEMINI_API_KEY` / `MAGAI_VERCEL_API_TOKEN` / Stripe keys present
- [ ] Database backup taken and verified restorable
- [ ] `/metrics` reachable from monitoring only, not the public internet

The app **refuses to start** in production if the first four are wrong. That is by
design — these are the misconfigurations most likely to ship unnoticed.

### Rolling back

```bash
# Application: redeploy the previous image tag.
# Schema (only if the release included a migration):
alembic downgrade -1
```

Every migration has a tested `downgrade()`; CI runs an up/down/up cycle against real
Postgres on every PR. Still check the migration's docstring first — one that drops a
column loses that data on downgrade.

## Monitoring

### Health probes

| Endpoint | Use | Behaviour |
|---|---|---|
| `/health/live` | Kubernetes liveness | Never touches dependencies — a database blip must not get the pod killed |
| `/health/ready` | Readiness / LB | 503 when Postgres, event Redis, or the broker is unreachable |
| `/health` | Dashboards, humans | Full per-dependency detail |

### Metrics

Prometheus on `/metrics`:

| Metric | Watch for |
|---|---|
| `magai_http_requests_total` | 5xx rate rising |
| `magai_http_request_duration_seconds` | p95 latency growth |
| `magai_pipeline_builds_total{outcome}` | `failed`/`started` ratio climbing |
| `magai_pipeline_build_duration_seconds` | Builds slowing toward the 900s soft limit |
| `magai_heal_checks_total{check_type,result}` | `failed` climbing, or `healed` spiking (mass rebuild) |
| `magai_heal_sweep_widgets` | Persistently equal to the batch size = falling behind |
| `magai_leads_captured_total` | The product's actual success metric |

### Suggested alerts

| Alert | Condition | Severity |
|---|---|---|
| API down | `/health/ready` failing 2 min | Page |
| Error spike | 5xx > 5% over 5 min | Page |
| Build failure rate | `failed / started` > 30% over 30 min | Investigate |
| Queue backing up | Broker depth rising 15 min | Investigate |
| Heal sweep saturated | `magai_heal_sweep_widgets` == batch size for 3 sweeps | Investigate |
| Cost anomaly | Analyze/build volume ≫ baseline | Investigate (abuse) |

### Logs

JSON lines with `request_id` on every record. To trace one request:

```bash
kubectl logs deploy/magai-api | grep '"request_id":"<id>"'
```

Users are shown the `request_id` in error responses, so a support ticket quoting one
retrieves the whole trail. Password, token, and secret fields are redacted by the
formatter.

## Backups

**Postgres is the only irreplaceable store.** Leads and accounts cannot be
regenerated. Redis is a queue and cache — losing it drops in-flight builds, which
users can retry. Widget build artifacts in `workspace/` can be regenerated by a
rebuild, though keeping them makes rollback instant.

```bash
# Nightly, retained 30 days, stored off-host.
pg_dump --format=custom --no-owner "$MAGAI_DATABASE_URL" > magai-$(date +%F).dump
```

```bash
# Restore into a scratch database and verify — an unverified backup is a guess.
createdb magai_restore_test
pg_restore --no-owner --dbname=magai_restore_test magai-2026-07-25.dump
psql magai_restore_test -c 'SELECT count(*) FROM users;   SELECT count(*) FROM leads;'
```

Do the restore drill on a schedule, not during an incident.

## Incident runbook

### API returning 503 `database_unavailable`

1. `curl /health` to confirm which dependency is down.
2. Check Postgres: reachable? connection limit hit? disk full?
3. Connection exhaustion is the common cause — look for a spike in API replicas
   against `max_connections`. Scale the pooler, not the app.
4. The API stays up deliberately during a database outage; readiness reports
   degraded and the balancer holds traffic back.

### Builds stuck in `building`

1. Is a worker alive? `celery -A app.platform.celery_app inspect ping`
2. Is the broker reachable? Enqueueing returns 503 when it is not.
3. A worker that died mid-build leaves the widget in `building`; **the API resets
   stale `building` widgets to `analyzed` on startup**, so restarting the API
   recovers them.
4. Check the widget's `build_error`, then have the user hit Retry.
5. If `build_already_running` appears in the logs, a per-widget lock is held. Locks
   have a TTL (`MAGAI_SELF_HEAL_LOCK_TTL_SECONDS`) and release themselves.

### Heal sweep not running

1. Is exactly one beat process alive?
2. Is `MAGAI_SELF_HEAL_ENABLED=true`?
3. Widgets past `MAGAI_SELF_HEAL_MAX_FAILURES` are skipped by design. Inspect them:

```sql
SELECT id, target_url, heal_failure_count, last_heal_check_at
  FROM widgets WHERE heal_failure_count >= 3;
```

4. After fixing the root cause, re-enable those widgets:

```sql
UPDATE widgets SET heal_failure_count = 0 WHERE id = '<widget-id>';
```

### A heal deployed a broken widget

The reason deploy history exists. Roll back from the widget's dashboard page, or:

```bash
curl -X POST https://api.example.com/api/widgets/<id>/rollback \
  -H "Authorization: Bearer <owner token>"
```

Rollback is instant — it re-points the embed at the previous immutable Vercel
deployment rather than rebuilding. If a systemic bad heal is affecting many widgets,
set `MAGAI_SELF_HEAL_ENABLED=false` and restart beat before rolling them back
individually.

### Suspected abuse / cost spike

1. Compare `magai_pipeline_builds_total` and analyze volume against baseline.
2. Identify the account:

```sql
SELECT user_id, count(*) FROM widgets
 WHERE created_at > now() - interval '1 hour'
 GROUP BY user_id ORDER BY 2 DESC LIMIT 10;
```

3. Tighten limits (`MAGAI_RATE_LIMIT_ANALYZE`, `MAGAI_RATE_LIMIT_BUILD`) and restart
   the API — they are read from configuration, not hard-coded.
4. Suspend the account without deleting anything:

```sql
UPDATE users SET is_active = false WHERE id = '<user-id>';
```

Tokens stop working immediately, because every request re-checks the user row.

### Suspected token or secret compromise

1. Rotate `MAGAI_SECRET_KEY` and restart the API. **This invalidates every issued
   token and signs all users out** — appropriate for a confirmed compromise.
2. For a single account: `UPDATE users SET is_active = false` to cut it off, then
   have them change password before re-enabling.
3. Rotate any exposed third-party key (Gemini, Vercel, Stripe) at the provider.
4. Grep logs for the affected `request_id`s to scope what was accessed.

## Routine maintenance

| Task | Cadence |
|---|---|
| Verify a backup restore | Monthly |
| Review dependency audit findings (CI runs weekly) | Weekly |
| Review heal failures (`heal_failure_count > 0`) | Weekly |
| Prune `workspace/` for deleted widgets | Monthly |
| Review rate limits against real usage | Quarterly |
| Rotate `MAGAI_SECRET_KEY` (plan for the forced sign-out) | Annually |

### Useful queries

```sql
-- Widgets needing attention.
SELECT id, title, status, build_error FROM widgets WHERE status = 'failed';

-- Self-heal effectiveness over the last week.
SELECT check_type, status, count(*) FROM widget_heal_events
 WHERE detected_at > now() - interval '7 days'
 GROUP BY 1, 2 ORDER BY 1, 2;

-- Widgets approaching their lead cap (upsell / cap-raise signal).
SELECT id, title, leads_count, lead_cap FROM widgets
 WHERE lead_cap > 0 AND leads_count::float / lead_cap > 0.8;
```
